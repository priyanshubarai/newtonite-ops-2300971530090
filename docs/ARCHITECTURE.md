# Architecture - Newtonite Operations Under Pressure

## 1. Overview

Newtonite Operations Under Pressure is an internal operational work-management application designed to replace fragmented coordination through chat, spreadsheets, email, and direct conversations. It enables users to create, assign, track, discuss, approve, resolve, and close operational work across multiple teams.

The application must provide clear visibility into: what work exists and why, current status and priority, current ownership, historical changes and decisions, and what requires attention next.

## 2. Approved Technology Stack

The following stack is authoritative and must be documented exactly as specified:

| Layer | Technology | Notes |
|---|---|---|
| Frontend | React + TypeScript | Client-side user interface |
| Frontend Server-State | TanStack Query | Data fetching, caching, synchronization |
| Backend | Node.js + Express + TypeScript | REST API server |
| Database | PostgreSQL (hosted on Neon) | Source of truth for all business data |
| ORM | Drizzle ORM | Typed schema definitions and queries |
| Migration Tooling | Drizzle Kit | Database schema migrations |
| Testing | Vitest + Supertest | Unit and integration testing |
| Local Development | Docker Compose | Local development environment |

**Important Constraints:**
- **Prisma is prohibited.**
- Architecture is a **modular monolith**.
- PostgreSQL is the source of truth for business data, audit history, idempotency records, and durable background-job intent.

### Database Provider (Neon)

PostgreSQL is hosted on **Neon**. The `DATABASE_URL` environment variable supplies the Neon connection string to both the runtime client and Drizzle Kit.

- **Runtime driver:** `drizzle-orm/neon-serverless` — the Neon WebSocket `Pool` from `@neondatabase/serverless`. Selected because atomic claims, optimistic concurrency, idempotency, and the transactional outbox require **interactive transactions**, which the `neon-http` driver does not support.
- **Migration connection:** Drizzle Kit connects to Neon directly over the standard PostgreSQL wire protocol using the same `DATABASE_URL`.
- **Node.js limitation:** The Neon serverless driver requires a `WebSocket` constructor under Node; the app sets `neonConfig.webSocketConstructor = ws` at startup.

## 3. Architectural Style

### Modular Monolith

The application uses a **modular monolith** architecture with clearly defined module boundaries. This approach:

- Keeps all code in a single deployable unit while maintaining logical separation of concerns
- Enables strong transactional consistency across modules using PostgreSQL transactions
- Prioritizes implementation speed and correctness over distributed deployment complexity
- Supports shared database access without introducing cross-service communication overhead

### Core Modules

The application is logically separated into the following modules:

| Module | Responsibility |
|---|---|
| **Authentication** | User authentication, session/token management for seeded demo users |
| **Authorization** | Team-scoped role-based access control, permission checks |
| **Work Items** | Work item lifecycle, state management, business rules |
| **Workflow** | State machine enforcement, transition validation |
| **Activity History** | Append-only audit trail of all significant changes |
| **Comments** | Collaboration through threaded discussions |
| **Idempotency** | Request deduplication and replay protection |
| **Background Processing** | Transactional outbox worker for asynchronous tasks |

### Outbox Jobs (Transactional Outbox)

For secondary asynchronous work, outbox jobs are inserted in the same transaction as business mutations.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| id | UUID | PK | Job identifier |
| job_type | Text | Required | Type of job to process |
| payload | JSONB | Required | Event payload |
| status | Enum `outbox_status` | Required, default PENDING | `PENDING, PROCESSING, COMPLETED, FAILED` |
| attempt_count | Integer | Required, default 0 | Number of retry attempts |
| max_attempts | Integer | Required, default 10 | Maximum retries (bounded) |
| next_attempt_at | timestamptz | Required, default now() | Next eligible processing time |
| processed_at | timestamptz | Nullable | Completion timestamp |
| last_error | Text | Nullable | Last error metadata |
| created_at / updated_at | timestamptz | Required, default now() | Timestamps |

**Index:** `oj_status_next_attempt_idx (status, next_attempt_at)` — pending-job lookup ordering.

#### Outbox processing — the Phase 8 worker

The consumer side of the outbox is a **separate process** (`backend/src/worker.ts`, run with `npm run worker`). It is not started by the HTTP server, so the API request path is unaffected by polling. The design was constrained by this table: **no column was added to it** (no migration), so the worker uses the existing columns only.

| Concern | Implementation |
|---|---|
| Eligibility | `status = 'PENDING' AND attempt_count < max_attempts AND next_attempt_at <= now()` and a supported `job_type`. |
| Claiming | `SELECT … FOR UPDATE SKIP LOCKED` followed by `UPDATE … SET status = 'PROCESSING'` in one short transaction; processing happens after commit, so no row lock is held across handler work. Two concurrent workers get disjoint batches. |
| Attempt accounting | The claim consumes one attempt (`attempt_count + 1`), so a job that repeatedly kills its worker is still bounded by `max_attempts`. |
| Lease | The schema has no lock/lease column, so `updated_at` (written from `now()` on every state change) acts as the lease timestamp. A job left `PROCESSING` longer than the lease timeout is treated as abandoned: back to `PENDING`, or `FAILED` if its attempts are exhausted. |
| Retry | Bounded exponential backoff with equal jitter; `next_attempt_at` is pushed into the future and the row stays `PENDING`. |
| Permanent failure | `status = 'FAILED'`, `processed_at` set, redacted `last_error`; never claimed again. |
| Delivery | **At-least-once.** Handler work is not inside the claim transaction, so a crash after the work but before the completion update can replay the job; handlers are idempotent and every outcome update is guarded on `status = 'PROCESSING'`. |

**Handler semantics.** There is no approved external integration (no email/webhook), so the handler performs the internal work a consumer must do before acknowledging an event — supported type, payload validated against the Phase 5 contract `{ workItemId, teamId, actorId, status, version }`, referenced work item exists, and event `teamId` matches the item's team — and records **processed/validated**, never "delivered". It is read-only and therefore idempotent by construction. A real consumer is added by extending `backend/src/outbox/handler.ts`.

## 5. Workflow & State Machine

### Approved Initial State Machine

`Open → In Progress → Awaiting Approval → Resolved → Closed`

### Workflow Rules

- **Server enforcement:** The server enforces allowed transitions. Clients must not bypass workflow rules by submitting arbitrary status values.
- **Approval authorization:** Only a Lead authorized for the item's team may perform the approval action (moving to/through approval steps as defined by the transition logic).
- **No reopening:** Reopening Closed items is out of scope.
- **Team-scoped:** All workflow authorization checks are scoped to the item's team.

## 8. Critical Behaviors & Correctness

The following behaviors must be correctly implemented and tested:

| Behavior | Description | Expected Outcome |
|---|---|---|
| **Concurrent claim** | Two concurrent requests claim the same unassigned item | Exactly one succeeds; the other receives 409 Conflict |
| **Stale update** | Update submitted with old version number | Rejected with 409 Conflict; newer data remains intact; version unchanged |
| **Idempotency** | Same request with same idempotency key retried | Produces one logical operation; returns original result |
| **Workflow enforcement** | Invalid transition or unauthorized approval attempted | `409 INVALID_TRANSITION` for an invalid edge; `403` for an under-privileged approval (`404` for a non-member) |
| **Resource authorization** | Access attempt from user not in item's team | Denied (403/404 as appropriate for concealment) |
| **Audit atomicity** | Activity event insert fails in same transaction as mutation | Entire transaction rolls back; work item mutation is not persisted |
| **Outbox claim concurrency** | Two workers (or one worker twice) claim overlapping batches | Claim rows are selected `FOR UPDATE SKIP LOCKED` in a short transaction; the returned batches are disjoint — no job is handed out twice |
| **Outbox lease recovery** | A claimed job's worker dies before recording an outcome | After the lease timeout the job becomes eligible again (or `FAILED` if attempts are exhausted), so it is never stuck in `PROCESSING` |
| **Outbox bounded retry** | A handler fails repeatedly | Transient errors reschedule with bounded exponential backoff; permanent errors and exhausted attempt budgets terminate at `FAILED` — no infinite retry or tight loop |
| **Outbox at-least-once / idempotency** | The same job is delivered more than once | The job is recorded once per claim; the handler is idempotent, so a replayed delivery produces no duplicate effect |
| **Outbox log/data safety** | A payload or credential appears in an error path | Logs emit primitives only (objects become `[omitted]`) and `last_error` is redacted and length-bounded; secrets never reach stdout or the database |

**Testing Requirements:**
- Use **real PostgreSQL** for transaction and concurrency integration tests (mock-only tests insufficient)
- Use **Vitest + Supertest**
- All tests must be runnable through a documented command
- Testing occurs throughout implementation; Phase 6 closes critical coverage gaps

### Outbox worker tests (Phase 8)

- **Unit (no database):** `src/outbox/events.test.ts` (event contract — job types and payload shape pinned to the Phase 5 producer), `src/outbox/backoff.test.ts` (bounds, jitter window, monotonic growth, defensive inputs), `src/outbox/logging.test.ts` (redaction, bounding, error categorisation, primitive-only log records).

- **Isolation:** claiming tests use a **unique per-run sentinel job type**, so a run can never claim a job belonging to another suite or the demo data; every job it inserts is deleted in `afterEach`. The real `work_item.*` handler is exercised directly against throwaway fixtures.

## 13. Transaction Boundaries

- **Business mutation + Activity event:** Must commit in the same PostgreSQL transaction
- **Business mutation + Outbox job:** Must commit in the same PostgreSQL transaction (for transactional outbox pattern)
- **Atomic claim:** Conditional UPDATE with WHERE clause (item unassigned AND team matches) to ensure exactly one winner
- **Optimistic concurrency:** UPDATE with version check (version = expected) AND increment version on success
- **Idempotency:** Serialize same-key requests with a transaction-scoped `pg_advisory_xact_lock` as the first statement, backed by a `(scope, key)` unique index; the record commits with the mutation. Same key + same payload replays the stored response; same key + different payload → `409 IDEMPOTENCY_KEY_REUSED`
- **Outbox claim:** Select-and-mark-`PROCESSING` (`FOR UPDATE SKIP LOCKED`) is its own short transaction. Handler work, retry scheduling, and the completion/failure update all happen **after** it commits, so no lock is ever held across processing. Each outcome update is additionally guarded on `status = 'PROCESSING'`, so a re-claimed (recovered) job cannot be completed twice.

### Open item raised in Phase 7 — dashboard views vs. available API

**Conflict:** §9 requires three preset views ("Assigned to Me", "Unassigned Urgent", "Awaiting My Approval") and Phase 7 of the roadmap also lists a comments section, an activity timeline, and cursor pagination. The Phase 7 authorisation limited scope to the endpoints that already exist and explicitly forbade new backend endpoints (outside an approved, verified blocking defect) and any scope expansion.

**Why it cannot be reconciled in-design:**

1. **"Unassigned Urgent" is not expressible.** `GET /items` accepts `assigneeId` only as a specific UUID; there is no "unassigned" filter. Expressing this view would require a new query parameter.
2. **"Awaiting My Approval" is only partially expressible.** `status=AWAITING_APPROVAL` is supported, but restricting results to teams where the caller is a Lead/Admin is not — the API does not accept a role predicate.
3. **Comments and activity history have no read endpoint.** `POST /items/:id/comments` is specified but unimplemented, and `GET /items/:id/activity` is unimplemented. The tables exist and are written transactionally. Building either UI requires new routes.
4. **Pagination is offset-based, not cursor-based.** `GET /items` implements `page`/`pageSize` with an exact `total`; the frontend matches the real contract rather than a cursor contract the API does not provide.

**What was delivered instead, without adding endpoints:** a single server-filtered, server-paginated list (team, status, priority, assignee, search, sort), detail with claim and workflow-transition actions, create and edit forms, and explicit conflict handling. No activity or comments UI is rendered, and the detail view states that activity history is unavailable rather than implying it exists.

**Decision needed:** either add the missing query parameters and read endpoints in a future phase, or amend §9/Phase 7 to accept the single filterable list as the delivered dashboard. Phase 7 made no conflicting change to the specification; it implemented the authorised subset and recorded the gap here.
